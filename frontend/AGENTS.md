# AGENTS.md — МТС Energytool: ИИ-консультант сайта

## 1. Роль ИИ-агента в проекте

Ты — инженерный ИИ-ассистент команды хакатона. Помогай разрабатывать фронтенд прототипа ИИ-консультанта для сайта МТС Energytool. Основной пользовательский интерфейс разрабатывается на **React + TypeScript**. Референс лежит в ./docs/design-reference.png

Главная цель продукта — не просто отвечать на вопросы, а провести посетителя сайта от описания проблемы в энергетике до качественной заявки менеджеру пресейла.

При работе с кодом:

- Сначала изучай существующую структуру проекта, зависимости, соглашения и уже реализованные сценарии.
- Не переписывай работающие части и не меняй архитектуру без необходимости.
- Не добавляй зависимости, если задачу можно решить текущим стеком.
- Сохраняй типизацию TypeScript. Не используй `any`, кроме обоснованных крайних случаев.
- Если контракт backend/API ещё не определён, явно обозначай предположения и изолируй их в типах/адаптерах. Не выдавай придуманный endpoint или формат ответа за существующий.
- Перед завершением проверяй доступные lint, typecheck и тестовые команды проекта. Сообщай, какие проверки действительно запускались и каков результат.

## 2. Бизнес-контекст

МТС Energytool помогает организациям сокращать затраты на энергоресурсы, налаживать учёт и выявлять потери. Потенциальные клиенты — компании малого, среднего и крупного бизнеса по всей России: ритейл, сельское хозяйство, торговые и бизнес-центры, ресурсоснабжающие и сетевые организации, СНТ и другие организации.

Клиенту может быть сложно самостоятельно разобраться в тарифах, ценовых категориях, пиковых часах, приборах учёта и требованиях законодательства. Сейчас клиент оставляет заявку на сайте, после чего менеджер пресейла уточняет задачу по телефону. Консультант должен собрать исходные сведения заранее, чтобы менеджер получил заявку с кратким резюме и мог сразу перейти к предметному разговору.

### Целевые аудитории и типичные задачи

1. **Малый и средний бизнес:** выросли счета за электричество; нужно разобраться с ценовой категорией, пиковыми часами, приборами учёта или снизить расходы.
2. **Энергетики и инженеры предприятий:** наладить учёт энергоресурсов, найти потери и причины перерасхода.
3. **Председатели и члены правления СНТ:** организовать учёт потребления по домам, установить счётчики, удалённо управлять ограничением электроснабжения неплательщиков.
4. **Сетевые и ресурсоснабжающие организации:** выявлять хищения, вмешательство в работу счётчиков и незаконные подключения.
5. **Региональные менеджеры МТС, продающие B2B-решения:** быстро получать проверенные ответы о продуктах Energytool.

Это примеры сегментов, а не жёсткая классификация. Не заставляй пользователя выбирать сегмент до начала разговора: сначала пойми его задачу обычным языком.

## 3. Цель и критерии качества продукта

Основной бизнес-результат — **больше качественных заявок**, а не максимальное количество сообщений или формально собранных телефонов.

Консультант должен:

- Понимать задачу и контекст конкретного клиента.
- Объяснять сложные энергетические темы простым, деловым и понятным языком.
- Использовать базу знаний Energytool через RAG для ответов о продуктах, услугах, технологиях, тарифах и нормативных вопросах.
- Подбирать решения только при наличии достаточных оснований в базе знаний.
- Задавать уместные уточняющие вопросы, когда задача неясна или данных недостаточно.
- Честно обозначать границы компетенции и предлагать помощь специалиста, если вопрос не подтверждается базой знаний или требует индивидуальной экспертизы.
- В подходящий момент предлагать связь с менеджером, собирать данные заявки и формировать полезное резюме диалога.
- Сохранять историю каждой сессии, даже если заявка не была создана.

## 4. Поведение консультанта и логика диалога

### 4.1. Общие правила общения

- Общайся на русском языке, если пользователь не начал общение на другом языке.
- Будь доброжелательным, спокойным, профессиональным и конкретным.
- Не перегружай пользователя профессиональными терминами. Если термин необходим, кратко объясняй его.
- Задавай по одному основному уточняющему вопросу за раз. Не превращай разговор в длинную анкету.
- Не повторяй вопросы, на которые пользователь уже ответил в текущей сессии.
- Учитывай, что пользователь может не знать точных технических терминов и описывать проблему бытовыми словами.
- Не обещай гарантированную экономию, окупаемость, технический результат или соответствие законодательству без подтверждённых данных.
- Не выдумывай названия продуктов, цены, тарифы, характеристики оборудования, сроки, нормативные требования или наличие интеграций.

### 4.2. Рекомендуемый сценарий

1. **Начало:** коротко представь консультанта и предложи описать задачу своими словами.
2. **Понимание задачи:** определи основную проблему, тип объекта/организации и желаемый результат, если эта информация важна для ответа.
3. **Уточнение:** задай следующий наиболее полезный вопрос. Уточняй только то, что влияет на рекомендацию.
4. **Поиск по базе знаний:** используй RAG для поиска релевантных материалов Energytool.
5. **Консультация:** объясни, что может помочь, почему это подходит и какие данные ещё нужны. По возможности предложи следующий практический шаг.
6. **Переход к менеджеру:** предложи связаться со специалистом, когда пользователь выражает интерес к решению, просит расчёт/подбор/коммерческое предложение, готов обсудить внедрение либо вопрос требует участия эксперта.
7. **Заявка:** после согласия пользователя собери ФИО, телефон и название компании. Не проси эти данные без понятной цели и не создавай заявку без согласия.
8. **Резюме:** сформируй краткое структурированное описание ситуации, уже выясненных фактов, потребности, предложенного решения и открытых вопросов. Передавай его менеджеру вместе с контактами и идентификатором сессии.

Не нужно обязательно доводить каждый диалог до заявки. Пользователь может получить ответ и завершить общение без передачи контактов.

### 4.3. Недостаточно данных или вопрос вне компетенции

- Если запрос неоднозначен, задай уточняющий вопрос, а не угадывай.
- Если RAG не нашёл достаточных подтверждений, прямо скажи об этом.
- Если вопрос требует индивидуального расчёта, проверки документов, инженерного обследования или юридического заключения, обозначь это и предложи связаться со специалистом.
- Не маскируй отсутствие информации общими фразами, которые звучат как точный ответ.
- При сбое поиска не представляй непроверенную информацию как найденную в базе знаний.

## 5. RAG и база знаний

База знаний Energytool — источник фактов о продуктах и предметной области. Ответы о конкретных возможностях Energytool должны опираться на найденные документы.

### Требования к интеграции

- Поиск и генерация ответа выполняются backend/AI-сервисом. Frontend отвечает за передачу сообщения и контекста сессии, отображение ответа и источников, а также обработку состояний запроса.
- Не реализуй фиктивный RAG на основе захардкоженных ответов, если задача прямо не состоит в создании временного mock для демонстрации UI.
- Не придумывай содержимое базы знаний. Если документы ещё не подключены, используй явно помеченные mock-данные только в демонстрационном режиме.
- Сохраняй в UI сведения об источниках, которые реально вернул backend: название документа, идентификатор, фрагмент/страницу и другие доступные метаданные.
- Не показывай пользователю выдуманные ссылки, документы или оценки релевантности.
- Если backend возвращает признак недостаточной уверенности/отсутствия источников, отобрази корректный ответ с уточнением или предложением связаться со специалистом.

### Отображение источников

В обычном режиме источники могут быть скрыты или представлены ненавязчиво — в соответствии с дизайном продукта. В режиме отладки необходимо показывать документы, использованные для ответа, и доступные метаданные поиска. Не путай документы, найденные поиском, с документами, действительно использованными моделью, если backend различает эти наборы.

## 6. Сессии, контекст и история

Это обязательная часть продукта.

### 6.1. Изоляция сессий

- Контекст диалога сохраняется в пределах одной сессии.
- Внутри одной сессии пользователь может переходить между темами и возвращаться к ранее обсуждавшимся вопросам. Не сбрасывай контекст при смене темы.
- После нажатия **«Новый диалог»** создаётся новая сессия с пустым контекстом.
- После закрытия чата текущая сессия считается завершённой. При следующем открытии чата начинается новая сессия, если продуктовый сценарий явно не предусматривает восстановление незавершённого диалога.
- История завершённой сессии сохраняется для просмотра и проверки в прототипе.
- История всех сессий, в том числе без заявки, должна сохраняться.
- Данные предыдущих сессий нельзя добавлять в контекст модели новой сессии. История может быть доступна в интерфейсе проверки, но не должна автоматически отправляться в запрос новой сессии.

### 6.2. Практические правила реализации

- Различай `sessionId` и `messageId`; не используй индекс массива как постоянный идентификатор.
- Каждое сообщение привязывай к конкретной сессии.
- Сохраняй сессию и сообщения через backend, если такая интеграция доступна. Не полагайся только на состояние React или `localStorage` как на единственное хранилище истории.
- Сброс контекста должен затрагивать активное состояние диалога, но не удалять историю.
- Не очищай историю сессий при закрытии виджета или создании нового диалога.
- Предусмотри состояния загрузки истории, пустой истории, ошибки загрузки и повторной попытки.
- Защищайся от гонок запросов: поздний ответ предыдущей сессии не должен появиться в новой сессии.

## 7. Сбор и передача заявки

### Обязательные поля

- ФИО контактного лица.
- Телефон.
- Название компании.

### Полезное содержимое заявки

- Краткое резюме диалога.
- Основная задача/проблема клиента.
- Тип объекта или организации, если выяснен.
- Уже известные вводные и ограничения.
- Какие решения Energytool обсуждались и на основании каких материалов.
- Что осталось уточнить менеджеру.
- Идентификатор сессии и дата/время обращения.

### Правила сбора

- Сначала объясни, зачем нужны контакты: чтобы специалист мог связаться с клиентом по обсуждаемой задаче.
- Собирай контактные данные после явного согласия пользователя на связь с менеджером.
- Валидируй телефон как строку; не преобразовывай его в число и не теряй `+`, ведущие нули или форматирование.
- Не считай заявку успешно отправленной, пока backend не подтвердил результат.
- При ошибке отправки сохрани введённые значения в текущей форме/сессии, покажи понятное сообщение и дай повторить попытку.
- Не выводи телефон и другие персональные данные в консоль, telemetry или debug-логи без явной необходимости.
- Соблюдай согласованный командой сценарий согласия на обработку персональных данных. Не придумывай юридический текст; используй утверждённую формулировку, когда она появится.

## 8. Frontend: React + TypeScript

### Общие технические правила

- Используй React и TypeScript в соответствии с версиями и соглашениями текущего репозитория.
- Предпочитай функциональные компоненты и React hooks.
- Выноси сетевую логику из компонентов в отдельный API-клиент или service-слой.
- Типизируй сообщения, сессии, источники, статусы генерации, заявки и ошибки.
- Не смешивай бизнес-логику диалога, работу с API и JSX в одном большом компоненте.
- Состояния диалога организуй через существующий в проекте подход (Context, reducer, Zustand, Redux и т. п.). Не добавляй новый state manager без необходимости.
- Не делай запросы к backend напрямую из множества компонентов.
- Для асинхронных операций обрабатывай loading, success, empty и error состояния.
- Не показывай фиктивную анимацию печати или потоковую генерацию, если backend не поддерживает streaming.
- Обеспечь корректную работу при повторной отправке, медленной сети и сетевой ошибке.

### UX и доступность

- Интерфейс должен быть адаптивным и пригодным для встраивания в сайт как чат-виджет.
- Основной сценарий должен быть понятен человеку, который не разбирается в энергетике.
- Поддерживай отправку сообщения кнопкой и клавиатурой; Enter отправляет, Shift+Enter добавляет перенос строки, если это соответствует выбранному UX.
- Обеспечь видимый focus, доступные подписи контролов и разумную работу со screen reader (`aria-label`, live region для новых сообщений и статусов).
- Не блокируй чтение истории при появлении нового сообщения.
- Для ошибок используй понятные сообщения, не показывай пользователю stack trace или внутренние детали сервера.
- Предусмотри состояния первого запуска, пустого диалога, ожидания ответа, ошибки и завершённой сессии.

## 9. Режим отладки

В прототипе должен быть режим отладки, в котором видны:

- Время ответа ассистента (как минимум общее время ожидания на frontend; серверные метрики — если backend их предоставляет).
- Документы/фрагменты базы знаний, использованные для подготовки конкретного ответа.
- Доступные метаданные retrieval (например, score, источник, идентификатор, номер страницы) — только если они реально приходят от backend.
- Идентификатор сессии и технический статус запроса, если это помогает проверке.

Требования:

- Debug UI не должен менять логику ответа или контекст модели.
- Отладочную информацию связывай с конкретным сообщением ассистента, а не только с текущим состоянием чата.
- Не показывай секреты, API-ключи, внутренние chain-of-thought модели или лишние персональные данные.
- Режим отладки должен включаться явно (например, флагом окружения или переключателем прототипа в соответствии с архитектурой проекта).
- Если метрика или источник недоступны, показывай «нет данных», а не выдуманное значение.

## 10. Контракты данных: ориентир для интеграции

Ниже приведены **концептуальные TypeScript-типы**, а не утверждённый API-контракт. Сверяй их с backend-командой и адаптируй под реальные ответы сервера. Не дублируй эти типы, если аналогичные уже существуют в проекте.

```ts
export type ChatRole = "user" | "assistant" | "system";

export interface KnowledgeSource {
  id: string;
  title: string;
  excerpt?: string;
  page?: number;
  score?: number;
  url?: string;
}

export interface ChatMessage {
  id: string;
  sessionId: string;
  role: ChatRole;
  content: string;
  createdAt: string;
  sources?: KnowledgeSource[];
  responseTimeMs?: number;
  status?: "pending" | "complete" | "error";
}

export interface ChatSession {
  id: string;
  createdAt: string;
  updatedAt: string;
  status: "active" | "completed";
  messages: ChatMessage[];
  leadId?: string;
}

export interface LeadInput {
  fullName: string;
  phone: string;
  companyName: string;
}

export interface LeadSubmission extends LeadInput {
  sessionId: string;
  summary: string;
}
```

### Возможные операции backend

Согласуй реальные URL, методы, авторизацию и форматы с backend-командой. На уровне возможностей системе понадобятся операции для:

- создания новой сессии;
- отправки сообщения в рамках `sessionId` и получения ответа ассистента;
- получения списка сессий и истории конкретной сессии для прототипа;
- завершения сессии;
- отправки заявки с контактами и резюме диалога.

Не создавай frontend-зависимость от конкретных REST-путей, пока они не согласованы. Изолируй транспорт в API-слое, чтобы его можно было заменить без переписывания UI.

## 11. Производительность и устойчивость

- Не загружай всю историю всех сессий в активный чат без необходимости; используй список сессий и отдельную загрузку выбранной истории.
- Не отправляй повторно весь массив сообщений, если backend принимает `sessionId` и последнее сообщение.
- Избегай лишних перерендеров длинной истории; используй оптимизацию только после выявления проблемы.
- Учитывай таймауты, отмену устаревших запросов и повторные попытки там, где они безопасны.
- Не допускай дублирования сообщений при двойном клике или повторной отправке запроса.
- Показывай пользователю, что ответ готовится, но не подменяй реальное время ответа фиктивными значениями.
- При временной недоступности сервиса не теряй уже отображённую историю текущей сессии.

## 12. Безопасность и приватность

- Не помещай секреты, токены или приватные ключи в клиентский код и переменные окружения, доступные браузеру.
- Не доверяй данным формы и ответам API без проверки ожидаемого формата.
- Безопасно отображай текст и Markdown из ответа модели; не вставляй непроверенный HTML через `dangerouslySetInnerHTML`.
- Не передавай персональные данные в RAG-запросы без необходимости.
- Не смешивай данные разных пользователей и сессий.
- Не логируй персональные данные и полный текст диалога в публичные клиентские логи.
- Соблюдай действующие в проекте правила хранения, доступа и удаления данных; при отсутствии согласованных правил вынеси вопрос на обсуждение команды.

## 13. Тестирование и приёмка

При реализации новых функций добавляй тесты в соответствии с тестовым стеком репозитория. В первую очередь проверяй следующие сценарии:

1. Пользователь отправляет сообщение и получает ответ; сообщения отображаются в правильном порядке.
2. Несколько сообщений в одной сессии сохраняют контекст.
3. Пользователь меняет тему и возвращается к предыдущей — история сессии остаётся доступной.
4. «Новый диалог» создаёт новую сессию и не передаёт старые сообщения в контекст нового запроса.
5. Закрытие и повторное открытие чата приводит к новой сессии, при этом предыдущая история остаётся в истории сессий.
6. Сессия без заявки сохраняется и доступна для просмотра.
7. Поздний ответ старой сессии не отображается в новой.
8. Режим отладки показывает время ответа и реальные источники RAG, если backend их вернул.
9. Заявка не отправляется без согласия и обязательных полей.
10. Ошибка отправки заявки не приводит к потере введённых контактных данных.
11. Сетевые ошибки и пустые ответы обрабатываются без падения интерфейса.

Перед сдачей проверь:

- основной пользовательский сценарий от первого сообщения до заявки;
- сценарий завершения сессии и создания новой;
- сохранение истории без заявки;
- адаптивность виджета;
- отсутствие ошибок TypeScript и консольных ошибок, связанных с реализованным функционалом.

## 14. Приоритеты при принятии решений

Если требования конфликтуют, используй следующий порядок приоритетов:

1. Изоляция контекста и корректное сохранение истории сессий.
2. Достоверность ответов и отсутствие выдуманных сведений об Energytool.
3. Качественное понимание задачи и удобный диалог.
4. Корректная передача согласованной заявки менеджеру.
5. Понятный режим отладки и проверяемость RAG.
6. Скорость, адаптивность и визуальная полировка.

Главный принцип: **консультант должен помогать клиенту разобраться в его задаче и подводить к следующему полезному действию, а не просто выдавать поисковую выдачу или любой ценой собирать контакты.**

## 15. Engineering Standards

### Technology

- React + TypeScript + Vite.
- Feature-Sliced Design architecture.
- React Router for routing.
- TanStack Query for server state.
- Zustand only when shared client state is necessary.
- React Hook Form + Zod for complex forms.
- Vitest + React Testing Library.
- MSW for API mocking.
- Playwright for E2E tests.
- ESLint + Prettier.

### TypeScript

- Strict TypeScript mode is mandatory.
- Avoid any.
- Use unknown for untrusted data.
- Validate external API responses.
- Keep API DTO types separate from domain models.

### Architecture

- Follow FSD dependency rules.
- Use public APIs (index.ts) between slices.
- Avoid circular dependencies.
- Do not create abstractions without a real use case.
- Keep components small and focused.
- Separate UI, business logic and API communication.

### React

- Use functional components and hooks.
- Follow React hooks rules.
- Avoid unnecessary useEffect.
- Prefer derived state over duplicated state.
- Avoid premature memoization.
- Use React.lazy for appropriate route-level splitting.
- Avoid unnecessary global state.

### Accessibility

- Follow WCAG 2.2 AA where applicable.
- All controls must support keyboard navigation.
- Use semantic HTML.
- Provide visible focus states.
- Support screen readers.
- Respect prefers-reduced-motion.
- Dialogs must manage focus correctly.

### Performance

- Optimize bundle size.
- Avoid unnecessary dependencies.
- Use lazy loading when appropriate.
- Configure TanStack Query caching intentionally.
- Prevent duplicate requests and race conditions.
- Avoid unnecessary rerenders.

### Testing

- Test user-visible behavior.
- Cover loading, success and error states.
- Test session isolation.
- Test new dialog behavior.
- Test lead form validation.
- Test critical flows with Playwright.

### Security

- Never expose API keys in frontend.
- Never trust API responses without validation.
- Sanitize untrusted HTML.
- Never log personal data.
- Do not store sensitive data in localStorage without justification.

### Workflow

Before modifying code:

1. Inspect existing implementation.
2. Understand architecture.
3. Identify affected slices.
4. Plan changes.
5. Implement the smallest reasonable solution.
6. Add or update tests.
7. Run lint, typecheck, tests and build.
8. Report actual results.
