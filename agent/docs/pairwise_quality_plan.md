## 1. Воспроизвести платформенную оценку локально — ✅ реализовано, ограничение подтверждено

Добавлен pairwise-судья:

- два раунда с изменением порядка ответов;
- шкала `0 / 0.25 / 0.5 / 0.75 / 1`;
- расчёт Match Rate, Win Rate и итогового Score;
- сохранение побед, поражений, ничьих и причин по каждому вопросу;
- вопросы с технической ошибкой судьи исключаются из метрик.

Формулы:

```text
Match Rate = средний балл по успешно оценённым вопросам
Win Rate = победы / (победы + поражения)
Score = 0.7 × Match Rate + 0.3 × Win Rate
```

Ничьи не участвуют в Win Rate. Если все сравнения завершились ничьей, Win Rate принимается равным `0.5`.

### Что реализовано

- `evals/pairwise_judge.py`: два раунда, смена порядка, пять значений шкалы, Match Rate, Win Rate, Score, JSON/CSV с причинами.
- `evals/run_sample_baseline.py`: воспроизводимый запуск учебного `sample_submission.zip` на выбранном CSV.
- `evals/holdout_questions.csv` и `evals/holdout_output.csv`: 12 новых вопросов и проверенные по базе эталоны.
- Ответы решения 54.628 заморожены в `evals/results/best_54_628_demo.csv` и `best_54_628_holdout.csv`.

### Роль golden и baseline

- Golden для demo: `data/demo_output.csv`.
- Golden для holdout: `evals/holdout_output.csv`.
- `sample_submission.zip` не подтверждён как официальный baseline и используется только для технической проверки оценки.
- Замороженные ответы 54.628 позволяют находить различия между версиями, но локальная победа над ними не доказывает рост платформенного балла.
- Настоящие baseline и golden платформы скрыты. Поэтому локальные результаты не обязаны быть транзитивными или совпадать с платформенной оценкой.

## 3. Объективно разобрать ошибки лучшей версии — ⬜ следующий шаг

Для demo и holdout нужно сравнивать ответы 54.628 с golden и официальной базой по проверяемым признакам:

- дан ли прямой ответ;
- сохранены ли необходимые числа, единицы и пороги;
- сохранены ли ограничения сегмента и оговорки;
- есть ли неподтверждённые утверждения;
- назван ли конкретный следующий шаг, если он требуется;
- учтены ли известные условия из истории.

Для каждой ошибки зафиксировать источник:

- **поиск:** нужного факта нет в фактическом контексте запроса;
- **генерация:** факт присутствует в контексте, но отсутствует или искажён в ответе;
- **неопределённость:** эталон требует сведения, которых нет в доступной базе.

Нельзя считать ошибкой поиска только по итоговому ответу: сначала проверяется точный текст, который попал в финальный промпт.

## 4. Точечный второй проход проверки фактов — ⬜ не начато

Если подтвердятся ошибки генерации, следующий контролируемый эксперимент выполняется поверх решения 54.628:

```text
исходный ответ 54.628
→ проверка по вопросу и фактическому контексту
→ исправление только доказанных ошибок
→ исходный ответ без изменений, если ошибок не найдено
```

Второй проход не должен заново писать, сокращать или улучшать стиль ответа. Разрешены только:

- восстановление пропущенного относящегося к вопросу факта из контекста;
- исправление числа, порога, ограничения или неподтверждённого утверждения;
- сохранение исходных корректных фактов, полноты и следующего шага;
- возврат исходного ответа, если нет конкретного доказательства необходимости правки.

Нельзя требовать от редактора сокращать общие рассуждения или автоматически переписывать каждый ответ: именно общая переработка v3 совпала с сильным платформенным ухудшением.

Минус — дополнительный LLM-вызов и рост времени. Нужно отдельно проверить общий лимит выполнения, стоимость и долю ответов, которые редактор оставляет без изменений.

## 5. Поиск менять только после доказанной ошибки контекста — ⬜ не начато

Текущего recall по документу и ключевому слову недостаточно. Перед изменением поиска нужно измерять:

- позицию нужного фрагмента;
- наличие всех обязательных фактов в фактическом контексте;
- количество посторонних фрагментов;
- точный текст финального промпта.

BM25, embeddings, реранкер и порядок контекста не менять без подтверждённой ошибки поиска.

## Правила использования demo и holdout

- Demo используется для объективного разбора ошибок и итеративной разработки.
- Holdout используется для проверки выбранного варианта без подгонки под его вопросы.
- Если решение изменено под конкретный holdout-вопрос, этот вопрос заменяется новым независимым вопросом.
- Pairwise-причины судьи являются подсказками, а не доказательством ошибки. Ошибка подтверждается текстом базы и golden.
- Приоритет имеют проверяемое покрытие фактов и ручной разбор всех отличий от 54.628.

## Критерии допуска к платформенной проверке

Локальные критерии позволяют только подготовить candidate, но не гарантируют улучшение:

1. Изменена только одна группа логики относительно 54.628.
2. Для всех изменённых ответов указано, какая подтверждённая ошибка исправлена.
3. Не появились новые неподтверждённые факты, потерянные числа, оговорки или нарушения ограничений.
4. Ответы, где не было доказанной ошибки, остались без изменений.
5. Demo и holdout проверены по объективным признакам; pairwise-результат не используется как самостоятельный критерий.
6. ZIP собран, скомпилирован и запущен с реальным API; прежний лучший архив сохранён.

После загрузки:

- результат выше 54.628 — новая версия становится лучшей;
- результат ниже 54.628 — немедленный откат к `data/best_submission.zip`;
- локальные метрики не могут отменить или перевесить платформенный результат.
