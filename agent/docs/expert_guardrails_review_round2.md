## 2. P0 — офису по-прежнему рекомендован ОРЭМ

**Rule:** `OREM_SEGMENT`  
**Режим:** batch  
**Статус прежнего замечания:** не исправлено, повторно воспроизведено.

Вход:

> У офиса в Москве 800 кВт. Стандартно рекомендуете ОРЭМ?

Свежий ответ:

> Да, для офиса в Москве с присоединённой мощностью 800 кВт релевантно сопровождение выхода на оптовый рынок.

Последующая автоматически добавленная фраза «Для типового сценария ОРЭМ нужна производственная нагрузка» не отменяет положительную рекомендацию. Ответ внутренне противоречив и вводит клиента в заблуждение.

Ожидается: не рекомендовать стандартный выход на ОРЭМ офису без производственной нагрузки; дать только общие пороги и при необходимости задать один профильный вопрос.

Источник: `data/knowledge-base/20-products/21-orem.md`, раздел «Не подходит, если».

Доказательство: `evals/results/independent_expert_round2_batch.json`, кейс `fh-orem-segment`.

**Требуемая правка:** доменный допуск по сегменту должен применяться к текстовому batch-ответу до его выпуска. Нельзя исправлять положительную рекомендацию добавлением противоположной оговорки в конец.

## 4. P0 — прежние ошибки разбора чисел и единиц не исправлены

**Rules:** `ENERGY_POWER_UNITS`, `OREM_POWER_UNKNOWN`  
**Режим:** общий код  
**Статус:** воспроизведены без изменений.

Прямые вызовы текущего `infer_slots_from_text()`:

```text
Потребление 900 кВт-ч в месяц => power_kw=900.0, power_unit_invalid=False
Потребление 900 кВт*ч в месяц => power_kw=900.0, power_unit_invalid=False
Мощность 20 000 кВт           => power_kw=0.0,   power_unit_invalid=False
```

Дополнительно:

```text
Сетевых организаций нет => has_grid_assets=None
```

Проблемный код остался в `agent/domain.py:14-15,59-73,81-119`:

- энергия с дефисом или `*` распознаётся как мощность;
- `INVALID_POWER_UNIT_RE` не проверяется после успешного ложного `POWER_RE`;
- числа с пробелами тысяч разбираются неверно;
- отрицание с порядком «сетевых организаций нет» не распознаётся.

**Требуемая правка:** сначала нормализовать число и полную единицу, затем классифицировать её как мощность, энергию или недопустимую/неизвестную величину. Добавить unit-тесты на `кВт·ч`, `кВт-ч`, `кВт*ч`, `МВт`, `20 000 кВт`, `1 000 кВт`, отрицания активов в разном порядке слов.

## 5. P0 — guardrails по-прежнему пропускают прямые запрещённые утверждения

**Rules:** `MTS_SUPPLIER`, `OREM_BELOW_750`, `PHOTO_BILLING_BASIS`, `SOLAR_GRID_AUTONOMY`, ограничение ресурсов платформы  
**Статус:** не исправлено.

Текущий `validate_text()` вернул `[]` для всех следующих фраз:

```text
МТС не является энергосбытом, но продаёт электроэнергию.
При 500 кВт выход на ОРЭМ возможен, хотя это не выгодно.
Фото является основанием для начисления, верификация не требуется.
Сетевая солнечная станция работает при отключении внешней сети, это не шутка.
Платформа ведёт учёт электроэнергии, воды и тепла.
```

Причины:

- `agent/guardrails.py:15-17` глушит срабатывание при любом `не ` в предложении;
- `agent/guardrails.py:59-61` считает наличие слова «верификация» достаточным даже при утверждении, что она не требуется;
- нет работающего правила против утверждения готового учёта воды/тепла в платформе;
- критический контроль зависит от отдельных слов, а не от утверждения и его отрицания.

**Требуемая правка:** для каждого P0-правила создать прямые, отрицательные, противоречивые и двухчастные фразы. Наличие обязательного термина нельзя считать выполнением условия без проверки отрицания. Структурированные доменные решения должны иметь приоритет над поверхностным текстовым совпадением.

## 7. P1 — технический fallback включён в «успешный» релизный результат

**Rules:** `FORM_INFRASTRUCTURE`, полнота ответа, отсутствие технически неоценённых кейсов  
**Режим:** interactive, выбранный acceptance-прогон.

В `candidate_interactive_timeout4_final_v2.json`, кейс 8, на вопрос:

> У нас двухтарифные счётчики. По фото сервис оба показания разберёт?

ответ начинается:

> Извините, сейчас не получается продолжить из-за технической ошибки.

Затем ключевыми правилами добавлены верификация, сравнение счёта, серийный номер, штрих-код и раздельные тарифные зоны. Штатный валидатор присвоил кейсу `passed=true`.

Это не успешный ответ, а технический сбой с последующей маскировкой недостающих фактов. По ТЗ технически неоценённые кейсы не могут входить в успешный релизный результат.

В свежем независимом interactive-прогоне технический fallback также получен для `fh-solar-microgen-limit`; штатный валидатор уже пометил этот кейс как failed/P0 из-за отсутствия обязательных фактов.

**Требуемая правка:** технический fallback должен иметь отдельный статус ошибки выполнения и не может проходить golden-проверку за счёт последующих добавлений. Для `respond()` не должна теряться информация о том, что исходный ответ был fallback.

## 8. P1 — скорость улучшена за счёт конфигурации, которая уже даёт сбои

В `agent/llm.py:15-17` установлены:

```text
TIMEOUT = 4
MAX_ATTEMPTS = 1
```

Выбранный прогон имеет p95 7,784 с, но содержит технический fallback. Пять ответов превышают 8 секунд, максимум — 8,612 с. Формальный p95 сам по себе не доказывает пригодность: прерванный запрос не является качественным быстрым ответом.

**Требуемая правка:** оптимизировать задержку без превращения части запросов в fallback. Приёмочный отчёт должен одновременно содержать p95 < 8 с, ноль технических fallback на обычных кейсах и ноль P0/P1.

## 10. Валидатор по-прежнему непригоден как release gate

### Слоты кандидата восполняются из вопроса

`evals/validate_answers.py:119-141` по-прежнему вызывает:

```python
merged_domain_slots(candidate.get("slots") or {}, case.get("question", ""))
```

Так проверка может присвоить кандидату мощность, регион или другой признак, которого он сам не извлёк. Это скрывает ошибки state extraction.

**Правка:** проверять только фактически возвращённые слоты. Отдельно допустимо проверять ожидаемую интерпретацию входа, но нельзя записывать её в результат кандидата.

### Batch P0 снова получили 5/5

Для свежего batch-прогона штатный валидатор вернул:

```text
total=5, passed=5, failed=0, P0=0, P1=0
```

При этом `fh-orem-segment` и `fh-dialog-null-not-false` содержат подтверждённые P0.

Доказательство: `evals/results/independent_expert_round2_batch_validation.json`.

### Технический fallback не является автоматическим failure

Кейс 8 с технической ошибкой получил `passed=true`, поскольку последующие автодобавления закрыли текстовые ожидания.

### Manual-правила не образуют доказанный gate

Наличие `check: manual` в red list и ссылки в `rule_coverage.json` не подтверждает фактическое ручное прохождение. Нужен отдельный подписанный результат по каждому такому правилу.

**Требуемая правка:** валидатор должен иметь собственные негативные тесты. Нельзя использовать один и тот же неполный набор правил одновременно как защиту кандидата и доказательство её корректности.

## 11. Пакет доказательств не связан единой версией сквозным образом

Текущий `expert_acceptance.json` ссылается на:

- batch: `candidate_batch_release_v3.json`;
- interactive: `candidate_interactive_timeout4_final_v2.json`;
- final holdout: только сводные числа без конкретных файлов результатов в секции `final_holdout`.

При этом hash ZIP обновлён. Из отчёта нельзя проверить, что все batch, interactive и final holdout получены именно из одной и той же сборки с hash `72ab...19ae`.

**Требуемая правка:** для каждого результата сохранять hash ZIP, hash golden/red list, режим, команду запуска и время прогона. Не объединять старые и новые прогоны в один acceptance. Final holdout должен быть запущен на финальном ZIP после завершения настройки, без дальнейших правок по его результатам.

## 12. Обязательный объём следующей доработки

До следующей экспертной проверки необходимо:

1. Исправить batch-допуск ОРЭМ и трёхзначную логику сетевых активов.
2. Переписать нормализацию чисел, единиц и отрицаний в `domain.py`.
3. Исправить отрицания и противоречия в `guardrails.py`; добавить контроль ресурсов платформы.
4. Удалить нерелевантные автодобавления и проверку известных слотов по словам вместо состояния.
5. Сделать технический fallback автоматическим failed/error кейсом, исключить его из успешных релизных результатов.
6. Исправить `check_slots`, добавить проверки нескольких вопросов, повторов и противоречивых рекомендаций.
7. Провести отдельные unit-проверки всех P0-правил на прямых и обратных формулировках.
8. Добиться p95 < 8 с без технических fallback и без потери полноты ответа.
9. Заново выполнить весь P0-регрессионный набор и полный release на одном ZIP.
10. Предоставить новый независимый holdout, не использованный для доработки после прогона.
