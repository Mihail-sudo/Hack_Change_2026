# План улучшения качества агента

Цель: повысить балл автоматической оценки без работы над интерфейсом и без лишней оптимизации Python/C++. Основное внимание — качество поиска по базе, полнота ответов и воспроизводимые измерения.

Текущий платформенный ориентир: лучший балл 0.5227, лидер — около 0.699. Локальные оценки судьи нельзя напрямую сравнивать с платформенным баллом.

## Выполнено

### 1. Разбор `sample_submission.zip`

Проверены точка входа, чтение входных файлов, API LLM/embeddings/reranker и параметры окружения.

Перенесены:

- `BASE_URL` и отдельный `EMBEDDER_API_KEY`;
- имена `train.csv`, `knowledge_base.zip`, `kb.zip`;
- поиск входных файлов в `DATA_DIR`, рабочем каталоге и рядом со скриптом;
- `MAX_WORKERS=3` по умолчанию;
- `TEMPERATURE=0.0` для сабмита;
- нейтральный fallback без сбора контактов.

Учебный поиск образца по первым 420 символам документа не копировали.

### 2. Разбиение базы и FAQ

- Документы делятся по заголовкам до `###`.
- Каждый вопрос FAQ становится отдельным фрагментом.
- Сохраняются название документа и родительский раздел.
- Получено 254 фрагмента вместо 156.

### 3. Контекст ограничений

- Обязательными оставлены только «Общие границы» и «Когда требуется специалист».
- Остальные разделы выбираются по релевантности.
- После выбора продукта добавляется только его раздел ограничений: ОРЭМ, платформа учёта, солнечные станции, поиск потерь или фото-показания.

### 4. Гибридный поиск и кэш

- Лексический поиск + BGE-m3 через RRF.
- Cosine similarity без новых зависимостей.
- Кэш embeddings в `data/knowledge-base-embeddings.json` не включается в ZIP.
- При недоступности embeddings используется лексический fallback.

### 5. Проверки и стабильность

- `evals/run_evals.py` поддерживает интерактивный агент и `--solution`.
- Поддержаны `--questions`, `--reference`, `--judge`, `TEMPERATURE`, `MAX_TOKENS`, `MAX_WORKERS`, `TOP_K`.
- Есть сравнение с предыдущим запуском и обработка недоступности судьи.
- Проведены 18 демо-вопросов с `demo_output.csv`.

Последний демо-прогон: 18/18 после отката BM25, recall поиска 18/18, средняя оценка генерации 4.28/5, максимум 6.46 секунды. Все ответы быстрее 8 секунд. Это не окончательная оптимизация и не заменяет платформенную оценку.

## Следующие задачи

### 1. Заменить самодельную лексику на BM25 + BGE-m3

Приоритет: высокий. Статус: откачено по запросу пользователя.

- BM25 удалён из зависимостей и кода.
- Восстановлена лексическая оценка по IDF.
- Гибрид с BGE-m3 через RRF сохранён.
- Дополнительное усиление заголовков и двухпроходный выбор отменены.
- Дальнейшая работа продолжена сразу с измерения recall отдельно от генерации.

### 2. Измерять качество поиска отдельно от генерации

Приоритет: высокий. Статус: ✅ выполнено.

Добавлен `evals/retrieval_report.py`, который фиксирует:

- нужный документ и раздел;
- попал ли он в контекст;
- какие источники и ключевые слова отсутствуют;
- была ли проблема в поиске или уже в генерации.

Результат: recall поиска 18/18. Отчёты сохраняются в `evals/results/retrieval_report.json` и `retrieval_report.md`.

### 3. Убрать переобучение на отдельные примеры

Приоритет: средний. Статус: не начато.

- Проверить, нужны ли отдельные жёсткие ответы для фото и квадрокоптеров после улучшения поиска.
- Проверить общий промпт на новых формулировках, а не только на знакомых сценариях.
- Не добавлять новые правила под конкретный вопрос без проверки остальных.

### 4. Рассмотреть реранкер после BM25 + BGE

Приоритет: условный. Статус: ✅ реализовано как опция, по умолчанию выключена.

- Поддержаны `/rerank`, `RERANKER_MODEL`, `RERANKER_API_KEY`, `RERANKER_TOP_N`.
- При отсутствии или недоступности реранкера используется прежний гибридный порядок.
- В Polza модель реранкера не найдена, поэтому качество проверяется на платформе.

### 5. Проверять стабильность перед сабмитом

Приоритет: постоянный. Статус: частично выполнено.

Для каждого изменения:

1. Прогнать 18 демо-вопросов с эталонами.
2. Сравнить оценку, замечания и время с предыдущим запуском.
3. Сделать два повторных прогона для проверки стабильности.
4. Сохранить JSON/CSV и записать платформенный результат отдельно.
5. Менять только одну группу логики между сабмитами.

## Ограничения

- Не добавлять C++ и новые фреймворки: сетевые вызовы LLM/embeddings доминируют над локальными вычислениями.
- Не менять одобренный интерфейс.
- Не включать вопросы, базу, индексы, кэш embeddings и секреты в ZIP.
- Не выполнять `git push` без явной просьбы пользователя.
- Не считать локальную оценку судьи эквивалентом балла платформы.
