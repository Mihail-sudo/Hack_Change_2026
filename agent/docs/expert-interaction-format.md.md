# Формат взаимодействия с экспертом домена: детальный пошаговый план

**Назначение документа:** определить эффективный формат работы с экспертом МТС EnergyTool для валидации и настройки ИИ-консультанта. Документ описывает конкретные шаги, артефакты и границы применимости.

**Контекст:** без эксперта домена RAG-бот будет уверенно воспроизводить запрещённые формулировки, путать пороги и выдавать рекомендации не той аудитории. База знаний (`20-portfolio.md`–`26-general.md`) содержит явные разделы «Чего утверждать нельзя», но их нужно превратить в работающую логику: фильтры retrieval, system prompt, post-generation валидаторы, триггеры эскалации.

---

## 7 конкретных ловушек, где LLM без эксперта почти наверняка ошибётся

| № | Ловушка | Что сделает LLM без эксперта | Что требует база |
|---|---|---|---|
| 1 | **Порог оптового рынка** (`21-orem.md`) | Скажет «прямой выход от 750 кВт» | 750 кВт — доступ; 20 МВт — прямое участие; ниже 750 — невозможно |
| 2 | **Единицы порога** (`21-orem.md`) | Перепутает кВт и кВт·ч, назовёт порог в «мегавольт-амперах» | Порог — в **присоединённой мощности**, не в потреблении |
| 3 | **Солнечная станция и резерв** (`23-solar.md`) | Скажет «панели обеспечат электричеством при отключении» | Сетевая станция **отключается вместе с сетью**; автономию даёт только гибридная с накопителями |
| 4 | **Окупаемость солнечной станции** (`23-solar.md`) | Назовёт одну цифру («4–6 лет») | Обязательно **две рамки вместе**: 7–9 лет по индикативной цене + 4–6 лет после проработки; «от 3 лет» — только как «в некоторых случаях» и только с обеими рамками |
| 5 | **Поиск потерь — кому** (`24-losses.md`) | Предложит энергосбытовой компании | Целевой клиент — **только электросетевая**; энергосбыту — только если есть сети на балансе |
| 6 | **Распознавание показаний — юридический статус** (`25-meter-reading.md`) | Скажет «показание можно использовать для начисления» | Распознанное показание — **дополнительное подтверждение**, в коммерческий учёт только после верификации; фото само по себе — не основание |
| 7 | **Персональные данные** (`26-general.md`) | Скажет «МТС не обрабатывает персональные данные» одной фразой про все продукты | Для потерь и фото — **не обрабатывает**; для платформы учёта — **решается договором**, юридический вопрос, бот не отвечает |

В каждом продуктовом файле есть разделы **«Факты, которые можно утверждать»** и **«Чего утверждать нельзя»** — это черновик guardrails, который нужно превратить в работающую логику.

## Шаг 0. Подготовка (до первой встречи, 0,5–1 день команды)

**Цель:** не тратить время эксперта на то, что можно прочитать.

1. Команда читает все 7 файлов базы (`20`–`26` + `00`–`17`).
2. Составляет **карту продуктов и задач** на основе `20-portfolio.md` — таблицу «задача клиента → продукт → ключевые слоты для уточнения».
3. Выписывает **список противоречий и неясностей** (например: как квалифицировать клиента — энергосбыт с сетями на балансе; что делать, если клиент называет мощность в кВт·ч).
4. Готовит **черновик red list** из разделов «Чего утверждать нельзя» — на подтверждение эксперту.

**Артефакт:** документ `expert-brief.md` с 15–25 конкретными вопросами.

## Шаг 1. Kickoff-консультация (2–3 часа, живая или видеозвонок)

**Формат:** структурированный Q&A по блокам, с записью и транскриптом.

### Блок A. Карта продуктов и квалификация (40 мин)

- Подтвердить/поправить матрицу «задача → продукт» из `20-portfolio.md`.
- Для каждой из 5 целевых аудиторий (малый/средний бизнес, энергетики, СНТ, сетевые/РСО, менеджеры МТС) — какие **3–5 первых вопросов** бот должен задать?
- Как отличить клиента, которому нужна **платформа учёта**, от того, кому нужен **поиск потерь**? Примеры формулировок.
- Как квалифицировать энергосбытовую компанию: когда предлагать поиск потерь, когда нет?
- Какие **обязательные слоты** собрать до рекомендации продукта? (Тип организации, мощность, регион, потребление, текущий учёт, ценовая категория, цель.)

### Блок B. Запрещённые формулировки и эскалация (40 мин)

- По каждому разделу «Чего утверждать нельзя» — **корректная альтернатива** для бота.
- Какие вопросы **всегда** триггерят «нужен специалист»? (Юридические, договорные, персональные данные на платформе учёта, конкретная цена, сроки, гарантии.)
- Какие вопросы **вне компетенции** бота полностью? (Техдокументация приборов, настройка систем учёта, проектирование схем.)
- Как формулировать отказ, чтобы он не звучал как «я не знаю»? 3–5 эталонных фраз.

### Блок C. Тон и язык под аудиторию (30 мин)

- Как объяснять **мощность vs потребление** владельцу малого бизнеса, инженеру и председателю СНТ? 3 версии.
- Как объяснять **ценовые категории** без терминов? Одна фраза на каждую из 6 категорий.
- Как объяснять **окупаемость** без обещаний? Эталонная формулировка для солнечной станции.
- Как объяснять **вероятностный характер поиска потерь** сетевой компании, не подорвав доверие к продукту?

### Блок D. Сбор заявки и резюме для менеджера (20 мин)

- Какие поля в резюме заявки **критичны** для менеджера пресейла?
- Какие формулировки в резюме недопустимы? (Например, «клиент хочет сэкономить 15%» — это обещание.)
- В какой момент диалога уместно предлагать оставить контакты? 3–5 триггеров.

**Артефакт:** транскрипт + заполненный `expert-brief.md` с ответами.

## Шаг 2. Асинхронные deliverables от эксперта (2–3 дня)

Эксперт готовит пакет документов строго под интеграцию в бота.

### 2.1. Red list (запрещённые утверждения) — таблица

| Запрещённая формулировка | Почему нельзя | Корректная альтернатива | Триггер эскалации? |
|---|---|---|---|
| «Прямой выход на опт от 750 кВт» | Смешение порога доступа и прямого участия | «От 750 кВт доступен выход, но до 20 МВт — через посредника» | Нет |
| «Станция обеспечит резерв» | Сетевая станция не работает без сети | «Резерв даёт только гибридная конфигурация с накопителями» | Нет |
| «Окупаемость 4–6 лет» | Одна рамка без второй — обещание | «По индикативной цене 7–9 лет, после проработки площадки обычно 4–6 лет» | Нет |
| «МТС не обрабатывает персональные данные» | Верно только для потерь и фото, не для платформы учёта | «По потерям и фото — не обрабатывает; по платформе учёта — решается договором, нужен специалист» | **Да** (по платформе) |
| «Показание по фото можно использовать для начисления» | Фото не основание для начисления | «Показание попадает в коммерческий учёт только после верификации» | Нет |
| «Точная стоимость проекта — X» | Цена считается под объект | «Ориентир — 70 руб/Вт, итог после обследования; расчёт бесплатный» | Нет |

**Как использовать:** каждый пункт red list — это либо (а) фильтр retrieval (не выдавать чанк с запрещённой формулировкой), либо (б) правило post-processing (переписать ответ), либо (в) триггер эскалации.

### 2.2. Escalation rules — дерево решений

ЕСЛИ вопрос про [юридические условия / договор / персональные данные на платформе учёта]
  → бот говорит: "Это решается договором, нужен специалист"
  → предлагает заявку

ЕСЛИ вопрос про [техническую документацию прибора / настройку системы учёта]
  → бот говорит: "Это вне моей компетенции"
  → предлагает связаться со специалистом

ЕСЛИ в базе нет ответа с уверенностью выше порога
  → бот задаёт уточняющий вопрос ИЛИ предлагает специалиста


### 2.3. Golden set — 50–100 эталонных вопросов и ответов

**Обязательно покрыть:**

- 5 целевых аудиторий × 3–5 вопросов = 15–25;
- 6 продуктов × 2–3 вопроса = 12–18;
- 10–15 **провокаций** (заведомо запрещённые формулировки — проверка red list);
- 10–15 **неоднозначных** (когда нужен уточняющий вопрос, а не ответ);
- 10–15 **вне базы** (когда нужна эскалация);
- 5–10 **многоходовых диалогов** (как в `demo_questions.csv` id 14–18).

Формат каждой записи:

| Поле | Что содержит |
|---|---|
| `question` | Вопрос или история диалога |
| `expected_task` | Задача клиента (из таксономии) |
| `expected_product` | Продукт(ы) Energytool |
| `must_include` | Обязательные факты (например, «750 кВт — порог доступа») |
| `must_not_include` | Запрещённые формулировки (ссылки на red list) |
| `clarifying_question` | Если нужен уточняющий вопрос — какой именно |
| `escalation` | Да/нет + причина |
| `reference_answer` | Эталонный ответ (150 слов макс.) |

**Как использовать:** ground truth для LLM-судьи и ручной проверки. Без golden set оценка «качества консультации» (25% онлайн-этапа) превращается в оценку «гладкости текста».

### 2.4. Список нормативных документов — с оговорками

Эксперт даёт перечень **только тех** документов, которые упомянуты в базе, с пометкой «что можно утверждать» и «чего нельзя»:

| Документ | Что регулирует | Что можно сказать | Что нельзя |
|---|---|---|---|
| 35-ФЗ «Об электроэнергетике» | Общая рамка | Упоминать как основание | Давать юридическое заключение |
| 522-ФЗ | Интеллектуальные системы учёта | «Требования к учёту действуют с 2022» | Толковать зоны ответственности |
| ПП РФ № 442 от 04.05.2012 | Розничные рынки, ценовые категории | Механику категорий | Юридическое заключение по договору |
| ПП РФ № 1172 от 27.12.2010 | Оптовый рынок | Пороги 750 кВт / 20 МВт | Гарантировать сроки процедур |
| ПП РФ № 948 от 08.06.2023 | Три способа учёта на ОРЭМ | «С 2025 доступна интеллектуальная схема» | Называть партнёра |
| ПП РФ № 2675-р от 26.09.2026 | Лимит отдачи в сеть 150 кВт | «До 150 кВт для юрлиц и ИП» | «Регионы поднимают лимит» (это федеральный уровень) |

**Ключевое:** эксперт не даёт «полный список НПА», а даёт **список с границами применимости** — что бот может процитировать, а что обязан переадресовать юристу.

### 2.5. Слот-чеклист по каждому продукту

Продукт: Выход на оптовый рынок
Обязательные слоты до рекомендации:
- присоединённая мощность (кВт)
- регион (проверить: не Камчатка / Магадан / Сахалин / Чукотка)
- текущий поставщик
- объём потребления (кВт·ч/мес) — для ориентира окупаемости
- класс напряжения
Если слот не заполнен → уточняющий вопрос, не рекомендация

Аналогично для платформы учёта, солнечной станции, поиска потерь, распознавания.

### 2.6. Глоссарий под аудитории

| Термин | Для малого бизнеса | Для инженера | Для СНТ |
|---|---|---|---|
| Присоединённая мощность | «Сколько вам выделено по документам» | «Максимальная мощность по акту ТП» | «Сколько киловатт выделено на товарищество» |
| Ценовая категория | «Способ, которым вам считают счёт» | «Категория расчёта на розничном рынке» | — |
| Окупаемость | «За сколько лет проект вернёт вложения» | «Срок простой окупаемости» | — |

## Шаг 3. Ревью-сессия с экспертом (1–2 часа, после первых прогонов бота)

**Формат:** эксперт смотрит 20–30 реальных диалогов бота (транскрипты из UI + документы, которые бот использовал в debug-режиме).

**Что делает эксперт:**

1. Отмечает **фактические ошибки** (перепутаны пороги, не та аудитория, не тот продукт).
2. Отмечает **пропущенные уточнения** (нужно было спросить, а бот ответил).
3. Отмечает **несостоявшиеся эскалации** (нужно было позвать специалиста, а бот ответил).
4. Отмечает **лишние эскалации** (бот испугался, хотя в базе ответ есть).
5. Предлагает **правки в промпт** и **правки в retrieval-фильтры**.

**Артефакт:** таблица `review-1.md` с 20–30 конкретными кейсами и пометками «что не так → как надо».

---

## Шаг 4. Финальная валидация (0,5 дня, перед защитой)

Эксперт проходит **основной сценарий консультации** от первого вопроса до заявки для каждой из 5 аудиторий и подтверждает:

- бот собрал нужные слоты;
- рекомендация продукта корректна;
- нет запрещённых формулировок;
- резюме для менеджера содержит то, что нужно;
- эскалации сработали там, где должны были.

**Артефакт:** подписанный чек-лист «готово к защите» — приложить к презентации как подтверждение экспертной валидации (плюс к критерию «Ценность для клиента и бизнеса» на финале).

## Шаг 5. On-call поддержка (по мере необходимости, весь хакатон)

Один канал (Telegram-чат команды с экспертом) для быстрых вопросов:

- «Клиент говорит „у нас 800 кВт, но потребляем 200 тыс. кВт·ч/мес“ — что отвечаем?»
- «Пришёл вопрос про тепловую энергию — это эскалация или „под доработку“?»
- «В базе есть противоречие между `21-orem.md` и `12-power-thresholds.md` — какая версия приоритетна?»

**Правило:** эксперт отвечает в течение 2–4 часов в рабочие часы; ответы складываются в `expert-faq.md` — это становится частью документации решения.

## Минимальный жизнеспособный формат (если эксперт есть только на 2–3 часа)

| Приоритет | Что | Зачем | Время |
|---|---|---|---|
| **1** | Kickoff-консультация по блокам A и B | Карта продуктов + red list + escalation rules | 1,5–2 ч |
| **2** | Golden set 30 вопросов | Основа для оценки и для промпта | 2–3 ч асинхронно |
| **3** | Ревью 15–20 диалогов | Поймать системные ошибки | 1 ч |
| **4** | Чек-лист «готово к защите» | Формальное подтверждение | 0,5 ч |

Этого достаточно, чтобы снять главные риски и не выглядеть на защите как «бот, который уверенно путает кВт и кВт·ч».

## Как встроить выход эксперта в технические артефакты

| Deliverable эксперта | Куда идёт в решении |
|---|---|
| Матрица «задача → продукт» | System prompt + few-shot examples + фильтр retrieval по типу задачи |
| Red list | Post-generation валидатор (regex/LLM-check на запрещённые фразы) + метаданные чанков (`allowed: false` для фрагментов с запрещёнными формулировками) |
| Escalation rules | Логика оркестратора: если тема ∈ {юридическое, ПДн на платформе, техдокументация} → escalate |
| Golden set | Автотесты + LLM-судья reference + ручная проверка |
| Слот-чеклист | State machine диалога: незаполненные слоты → уточняющие вопросы |
| Глоссарий | Few-shot для разных аудиторий (определяется по первым репликам) |
| Список НПА с оговорками | Retrieval по метаданным (`source: regulation`, `can_quote: true/false`) |
| Ревью-таблица | Правки в промпт, retrieval, порог уверенности |

## Итог

**Эксперт домена нужен не как «консультант вообще», а как владелец трёх вещей:**

1. **Границ допустимого** (red list + escalation rules);
2. **Критериев качества** (golden set + рубрика для судьи);
3. **Карты задач и продуктов** (матрица + слоты + глоссарий).

Без него RAG найдёт «похожий» чанк, LLM гладко перескажет — и бот уверенно скажет «прямой выход от 750 кВт», «панели дадут резерв» и «фото можно использовать для начисления». Каждая из этих фраз — прямой минус по критериям «Качество консультации» и «Ценность для клиента», и каждая явно запрещена в базе знаний, которую команда получила.
