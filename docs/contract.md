# Контракт между частями системы

Версия: 0.5 (диалог и заявка + админ-панель, 12 ноября 2026)
Любое изменение — сначала здесь, потом в коде, и с предупреждением в чате команды.

Этот файл описывает только **стыки** между частями: что одна часть передаёт другой. Как каждая часть устроена внутри, решает тот, кто её делает.

```
Виджет (Женя) ──HTTP──▶ API (Миша) ──вызов функции──▶ Агент (Елеазар) ──▶ LLM
                              │
                              ├──▶ Telegram менеджеру (Миша)
                              │
Админ-панель (Женя) ──HTTP───┘   те же данные диалогов, управление режимом

cli.py (терминал) ──вызов функции──▶ Агент      ← та же функция, для разработки и тестов
```

---

## 1. Агент ↔ API

Агент — Python-пакет `agent`. API вызывает две функции и больше ничего не знает об устройстве агента.

### `respond` — ответ на сообщение клиента

```python
from agent import respond

result = respond(message: str, state: dict | None) -> AgentResult
```

**Вход:**
- `message` — текст последнего сообщения клиента, как он его ввёл.
- `state` — состояние диалога, которое агент вернул на прошлом шаге. Для нового диалога `None`.

**Выход `AgentResult`** (словарь):

| Поле | Тип | Что это |
|---|---|---|
| `reply` | `str` | Текст ответа клиенту. Показывается как есть. |
| `state` | `dict` | Новое состояние. API сохраняет его **целиком и без изменений** и передаёт на следующем шаге. |
| `sources` | `list[str]` | Пути документов официальной базы, использованных при ответе, относительно `data/knowledge-base/`. |
| `action` | `dict` | Логическое действие для виджета: `type` и опциональный `manager_brief`. |
| `actions` | `list[dict]` | Внешние действия, которые должен выполнить API (см. ниже). Может быть пустым. |
| `done` | `bool` | `true`, если диалог завершён (лид передан или клиент попрощался). |

`action.type`: `answer` — ответ по теме; `clarify` — нужно уточнение; `show_form` — показать форму контактов; `out_of_scope` — вопрос вне компетенции; `handover` — заявка готова к передаче. `manager_brief` заполняется при `show_form` и `handover`, если уже есть содержательный контекст диалога.

### `LLMClient` — адаптер для backend

```python
from agent import LLMClient

client = LLMClient(system_prompt="Ты — онлайн-консультант...")
result = client.get_response(request)
```

Запрос содержит `messages` (предыдущая история), `new_message` и необязательный `session_state`. Адаптер возвращает:

```json
{
  "reply": "текст",
  "sources": ["20-products/22-askue.md"],
  "action": {"type": "clarify", "manager_brief": null},
  "session_state": {"...": "состояние для передачи в следующий запрос"}
}
```

`session_state` backend сохраняет без изменений. Дополнительный системный текст `system_prompt` дополняет, но не отменяет правила безопасности и базы знаний агента.

### `build_lead` — лид из формы контактов

```python
from agent import build_lead

lead = build_lead(state: dict | None, contact: dict) -> dict
```

Нужна для `POST /lead` (раздел 2): клиент оставил контакты в форме, а не в диалоге. API передаёт сохранённый `state` сессии (или `None`, если диалога не было) и контакты из формы, агент собирает лид по формату раздела 4 из того, что успел узнать.

Отдельная функция нужна, потому что API не читает `state` (правило ниже), а значит, сам не может достать оттуда слоты и историю.

### Правила

- `state` для API — «чёрный ящик». API не читает и не меняет его поля. Это даёт агенту право менять структуру состояния, не ломая API.
  **Исключение — режим оператора:** пока диалог перехвачен админом (раздел 3), агент не вызывается, и API сам дописывает реплики в `state.history` в формате `{"role": "user" | "assistant", "content": str}`. Поэтому агент обязуется держать `history` списком таких объектов. Остальные поля `state` API не трогает.
- `state` сериализуется в JSON: только строки, числа, bool, `null`, списки, словари.
- Агент не пишет в базу и не отправляет сообщения сам. Всё, что меняет внешний мир, он возвращает в `actions`, а выполняет вызывающий код: API на сервере или `cli.py` в терминале (там лид пишется в `leads/*.json`).
- Если агент упал с исключением, API отвечает клиенту запасной фразой (раздел 2) и пишет ошибку в лог. Сохранённое состояние при этом не перезаписывается.
- Полный транскрипт диалогов API пишет в свою базу сам (таблицы `dialogs` / `dialog_messages`), независимо от `state`. Для виджета и админки транскрипт — единственный источник истории: `state` живёт в Redis с TTL и для чтения наружу не предназначен.

### Действия (`actions`)

```json
{"type": "handoff", "lead": { ...объект лида, раздел 4... }}
```
Передать лид менеджеру: сохранить в базу и отправить в Telegram. Пока это единственный тип действия. Новые типы добавляются только через этот документ.

### Заглушки для разработки (пока агента нет)

```python
EXAMPLE_LEAD = {...}  # пример лида из раздела 3

def respond(message, state):
    state = state or {"turns": 0}
    state["turns"] += 1
    actions = [{"type": "handoff", "lead": EXAMPLE_LEAD}] if state["turns"] == 3 else []
    return {"reply": f"[заглушка] Вы написали: {message}", "state": state,
            "actions": actions, "done": state["turns"] == 3}

def build_lead(state, contact):
    return {**EXAMPLE_LEAD, "contact": {**EXAMPLE_LEAD["contact"], **contact}}
```
На третьем сообщении заглушка возвращает тестовый `handoff`, чтобы проверить отправку в Telegram.

## 2. Виджет ↔ API

Все запросы и ответы — JSON, кодировка UTF-8.

### `POST /chat`

Запрос:
```json
{
  "session_id": "строка, генерирует виджет (uuid4) и хранит до конца диалога",
  "message": "текст клиента"
}
```

Ответ `200`:
```json
{
  "reply": "текст ответа",
  "done": false,
  "mode": "bot"
}
```

- `mode`: `"bot"` — обычный режим, `"admin"` — диалог перехвачен оператором (раздел 3). В этом случае `reply` пустой: сообщение клиента доставлено, ответ придёт от оператора через `GET /chat/{session_id}/messages`.
- `session_id` новый → API создаёт сессию и вызывает агента с `state = None`.
- Пустое сообщение или длиннее 2000 символов → `400` с `{"error": "..."}`.
- Ошибка агента или LLM → `200` с запасным ответом:
  `{"reply": "Извините, сейчас не получается ответить. Оставьте, пожалуйста, телефон, и менеджер свяжется с вами.", "done": false, "fallback": true, "mode": "bot"}`.
  Виджет при `fallback: true` может сразу показать форму контактов.
- Каждая реплика (клиента и бота) дополнительно пишется в транскрипт диалога в базе.

### `POST /chat/handoff`

Клиент позвал оператора (кнопка «Позвать оператора» в виджете).

Запрос:
```json
{
  "session_id": "тот же, что в чате"
}
```

Ответ `200`: `{"ok": true}`

- Идемпотентно: повторный вызов не перезаписывает время первого обращения.
- Диалог появляется в админ-панели с пометкой. Пока оператор не перехватил диалог, **бот продолжает отвечать** как обычно.
- Если диалога с таким `session_id` ещё не было, он создаётся.

### `GET /chat/{session_id}/messages?after_id=0`

История реплик диалога из базы (транскрипт). Основной сценарий — поллинг ответов оператора, когда `mode == "admin"`.

Ответ `200`:
```json
{
  "session_id": "...",
  "mode": "admin",
  "messages": [
    {"id": 7, "role": "user", "author": "client", "content": "...", "created_at": "..."},
    {"id": 8, "role": "assistant", "author": "admin", "content": "...", "created_at": "..."}
  ]
}
```

- `role`: `"user"` | `"assistant"`; `author`: `"client"` | `"bot"` | `"admin"` — виджет может по-разному оформлять реплики бота и оператора.
- `after_id` — вернуть только реплики с `id` больше указанного (инкрементальный поллинг).
- Если диалога не было — `200` с пустым списком и `mode: "bot"`.

### `POST /chat/reset`

Сброс диалога (кнопка «Начать заново»).

Запрос:
```json
{
  "session_id": "тот же, что в чате"
}
```

Ответ `200`: `{"ok": true}`

- Удаляет сохранённое состояние сессии.
- `session_id` не меняется: следующее сообщение с тем же id начинает диалог заново (`state = None`). Виджету не нужно генерировать новый id.
- Если сессии не было, ответ всё равно `200`.

### `GET /chat/{session_id}`

Диагностика: вернуть сохранённое состояние сессии.

Ответ `200`:
```json
{
  "session_id": "...",
  "state": { "...": "..." }
}
```

- Если сессии нет или истёк TTL — `state: null`.
- `state` — чёрный ящик агента, эндпоинт нужен только для проверки.

### `POST /lead`

Запасной путь: клиент заполнил форму контактов в виджете, а не в диалоге.

Запрос:
```json
{
  "session_id": "тот же, что в чате (если диалог был)",
  "name": "", "company": "", "phone": "", "email": "",
  "consent_pd": true
}
```
- Нужно хотя бы одно из `phone` / `email`.
- `consent_pd` обязателен и должен быть `true`, иначе `400`.
- API вызывает `build_lead(state, contact)` (раздел 1) и выполняет передачу лида так же, как при `handoff`.

Ответ `200`: `{"ok": true}`

### `GET /health`
Ответ `200`: `{"ok": true}`. Нужен для Docker и чтобы перед защитой быстро проверить, что всё живо.

## 3. Админ-панель ↔ API

Панель оператора — отдельный фронтенд (зона Жени). Общается с тем же API по HTTP, поллингом (SSE и WebSocket в MVP нет). Пока без авторизации: эндпоинты лежат под `/admin` и открыты; закрыть токеном — до выката наружу.

Общая модель: диалог может находиться в режимах `bot` (отвечает агент) и `admin` (перехвачен оператором). Режим и флаг «клиент позвал оператора» живут в базе API, а не в `state`.

### `GET /admin/dialogs`

Список всех диалогов (это же — «все сохранённые диалоги»). Порядок — по времени последней реплики, новые сверху.

Ответ `200`:
```json
{
  "dialogs": [
    {
      "session_id": "...",
      "mode": "admin",
      "handoff_requested_at": "2026-11-11T10:00:00+00:00",
      "created_at": "...",
      "updated_at": "...",
      "messages_count": 12,
      "last_message": "текст последней реплики или null"
    }
  ]
}
```

- `handoff_requested_at` — время вызова оператора клиентом (`null`, если не звали). Сбрасывается при перехвате.

### `GET /admin/dialogs/{session_id}?after_id=0`

Транскрипт одного диалога, реплики в том же формате, что и в `GET /chat/{session_id}/messages`.

Ответ `200`:
```json
{
  "session_id": "...",
  "mode": "admin",
  "handoff_requested_at": null,
  "created_at": "...",
  "updated_at": "...",
  "messages": [ {"id": 1, "role": "user", "author": "client", "content": "...", "created_at": "..."} ]
}
```

- Диалога нет → `404`.
- `after_id` — для инкрементального поллинга новых реплик.

### `POST /admin/dialogs/{session_id}/takeover`

Перехватить диалог: `mode` → `"admin"`, флаг вызова оператора сбрасывается. С этого момента `POST /chat` не вызывает агента.

Ответ `200`: `{"ok": true, "mode": "admin"}`

- Диалога нет → `404`. Идемпотентно: перехват уже перехваченного — `200`.

### `POST /admin/dialogs/{session_id}/release`

Вернуть диалог боту: `mode` → `"bot"`. Агент продолжит с полным контекстом, включая реплики оператора (они дописаны в `state.history` как `assistant`).

Ответ `200`: `{"ok": true, "mode": "bot"}`

- Диалога нет → `404`. Идемпотентно.

### `POST /admin/dialogs/{session_id}/messages`

Реплика оператора клиенту. Виджет получает её через `GET /chat/{session_id}/messages`.

Запрос: `{"content": "текст от 1 до 2000 символов"}`

Ответ `200`: объект реплики (`id`, `role: "assistant"`, `author: "admin"`, `content`, `created_at`).

- Диалога нет → `404`.
- Диалог не перехвачен (`mode == "bot"`) → `409`: сначала `takeover`.

### `GET /admin/leads` и `GET /admin/leads/{id}`

Лиды из базы: выжимка диалога, контакты и статус доставки в Telegram.

`GET /admin/leads` — список, новые сверху:
```json
{
  "leads": [
    {
      "id": 1,
      "question": "выжимка из диалога",
      "name": null,
      "contact": "+7 900 000-00-00",
      "contact_type": "phone",
      "status": "delivered",
      "error": null,
      "created_at": "..."
    }
  ]
}
```

`GET /admin/leads/{id}` — один лид того же формата; нет → `404`.

## 4. Лид (передаётся менеджеру)

Формат утверждает Виталий. Поля ниже — черновик.

```json
{
  "lead_id": "uuid",
  "created_at": "2026-11-09T15:30:00+03:00",
  "session_id": "...",
  "source": "chat",

  "contact": {
    "name": "Иван Петров",
    "company": "СНТ «Рассвет»",
    "role": "председатель правления",
    "phone": "+7 900 000-00-00",
    "email": null,
    "preferred_channel": "телефон"
  },
  "consent_pd": true,

  "segment": "snt",
  "problem": "неплательщики и подозрение на подключения в обход счётчиков",
  "slots": {
    "units": 120,
    "meters_installed": "да, на столбах",
    "meter_models": null
  },

  "recommended": [
    {"product_id": "askue_snt", "reason": "120 участков, проблема с неплательщиками и хищениями"}
  ],

  "summary": "3–5 предложений для менеджера: кто клиент, что болит, что предложено, о чём договорились.",
  "tags": ["АСКУЭ", "СНТ", "хищения"],
  "priority": "normal",

  "transcript": [
    {"role": "client", "text": "..."},
    {"role": "bot", "text": "..."}
  ]
}
```

**Правила:**
- `lead_id` и `created_at` заполняет API при сохранении. Агент может оставить их `null`.
- `source`: `"chat"` — лид собран в диалоге, `"form"` — из формы контактов.
- `contact`: обязательно хотя бы одно из `phone` / `email`. Остальные поля могут быть `null`.
- `consent_pd` всегда `true`. Без согласия лид не создаётся (152-ФЗ).
- `segment` — одно из значений таблицы ниже.
- `product_id` — только идентификаторы из таблицы ниже. Агент не придумывает продукты.
- `slots` — словарь, набор полей зависит от сегмента (`data/segments.yaml`). Чего клиент не говорил — `null`, а не догадка.
- `summary` пишет агент. Менеджер должен понять ситуацию, не открывая `transcript`.
- `priority`: `"normal"` или `"high"`. Правило, когда ставить `high`, определит Виталий.

### Сегменты клиентов (черновик, окончательный список — в `data/segments.yaml`)

| `segment` | Кто это |
|---|---|
| `energy_sales` | Энергосбытовая компания, гарантирующий поставщик |
| `grid` | Сетевая организация |
| `industry` | Производство, промышленное предприятие |
| `business` | Бизнес-центр, магазин, кафе, офис |
| `uk` | Управляющая компания, ТСЖ, ЖКХ |
| `snt` | СНТ, дачное товарищество |
| `vodokanal` | Водоканал, водо- и теплоснабжение |
| `other` | Не удалось определить |

### Продукты (из `data/services_kb.md`)

| `product_id` | Продукт |
|---|---|
| `askue_cloud` | Облачная платформа учёта (АСКУЭ, «Энергосфера в облаке МТС») |
| `askue_snt` | АСКУЭ для СНТ |
| `commercial_losses` | Поиск коммерческих потерь |
| `mining_detection` | Выявление майнинговых ферм |
| `vodokanal` | Цифровой водоканал |
| `meter_photo` | Распознавание показаний счётчиков по фото |
| `termokontur` | Термоконтур |
| `solar` | Солнечные электростанции под ключ |
| `orem` | Выход на оптовый рынок электроэнергии (ОРЭМ) |
| `hourly_metering` | Почасовой учёт для малых точек поставки (уточнить, входит ли в кейс) |

Если продукт добавляется или убирается — меняются и `data/services_kb.md`, и эта таблица.

## 5. Сообщение менеджеру в Telegram

Собирает API из лида. Пример:

```
🔔 Новый лид · СНТ
Иван Петров, председатель правления
СНТ «Рассвет»
📞 +7 900 000-00-00

Проблема: неплательщики, подозрение на подключения в обход счётчиков
Предложено: АСКУЭ для СНТ
Детали: 120 участков, счётчики на столбах

Резюме: ...
#АСКУЭ #СНТ #хищения
```
Название продукта берётся из таблицы продуктов (раздел 3) по `product_id`. Полный JSON лида хранится в базе, в Telegram — только этот текст.
