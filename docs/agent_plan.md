# План разработки агента

Этапы идут по порядку: каждый опирается на предыдущий. У каждого этапа есть критерий «готово» — пока он не выполнен, следующий не начинаем.

Минимум до выхода кейса (9 ноября): этапы 0–3. Если успеваем — 4–5. Этапы 6–7 можно доделывать в первые дни хакатона. Этап 7 (стенд) можно начинать параллельно с 4–6: чем раньше он появится, тем меньше ручных проверок.

Статусы: ⬜ не начат · 🟨 в работе · ✅ готово

## ✅ Этап 1. Минимальный чат

**Цель:** сквозная цепочка «ввод → модель → ответ» в правильной форме.

- [x] `agent/llm.py`: `call_llm(messages, **params)`, ключ и модель из `.env`
- [x] `agent/agent.py`: `respond(message, state)` → `reply`, `state`, `actions`, `done`; история диалога в `state`
- [x] `cli.py`: цикл ввода и вывода; выполнение `actions` (запись лида в `leads/`)
- [x] `prompts/system.md`: простой промпт «ты консультант EnergyTool»

**Готово, когда:**
- бот ведёт диалог и помнит сказанное раньше;
- два диалога, запущенные вперемешку с разными `state`, не путаются.

**Подводный камень:** соблазн сразу писать умную логику. Цель этапа — правильный скелет, а не ум.

## ✅ Этап 2. База знаний

**Цель:** бот знает продукты и не выдумывает.

- [x] `agent/catalog.py`: `load_catalog()` читает `data/services/*.md` и `data/shop/shop_kb.md`, пропуская ошибочные выгрузки
- [x] `prompts/system.md`: роль + база знаний + правила:
  - только факты из базы;
  - цены только «от» и со ссылкой на менеджера;
  - один вопрос за раз;
  - не знаешь — так и скажи и предложи связь с менеджером

**Готово, когда:**
- на вопросы про СНТ, водоканал, солнечные панели бот отвечает по базе;
- на «сколько стоит поиск потерь» говорит «по запросу», а не называет число;
- на вопрос о том, чего в базе нет, не выдумывает.

**Подводный камень:** проверять только «правильные» вопросы. Обязательно спросить то, чего в базе нет.

**Проверено с LLM:** СНТ, водоканал, солнечные панели, цена по запросу и два неизвестных продукта. Десять других страниц услуг всё ещё содержат блокировку и не попадают в каталог до получения валидной выгрузки.

## ⬜ Этап 3. Слоты и этапы диалога

**Цель:** бот ведёт клиента по сценарию, а не просто отвечает. Ядро агента.

Зависит от Виталия: `data/segments.yaml` (хотя бы черновик).

- [ ] `data/segments.yaml`: сегмент → обязательные слоты
- [ ] `agent/state.py`: слоты, текущий этап, слияние новых слотов с известными
- [ ] `prompts/extract_slots.md` + вызов модели с JSON-схемой на каждое сообщение
- [ ] Код определяет этап: выяснение → подбор → контакты → передача
- [ ] Генерация ответа получает этап и список недостающих слотов

**Готово, когда:**
- бот не переспрашивает то, что клиент уже сказал;
- не предлагает решение, пока не знает сегмент и проблему;
- если клиент выложил всё в первом сообщении — сразу переходит к подбору.

**Подводный камень:** новое `null` из извлечения стирает уже известное значение. При слиянии `null` игнорируется.

## ⬜ Этап 4. Подбор решения

**Цель:** бот предлагает правильный продукт и объясняет почему.

- [ ] Правила допустимости продуктов — в данных (`data/`), например:
  - поиск коммерческих потерь — только при наличии АСКУЭ;
  - выход на ОРЭМ — только от 750 кВт;
  - облако по операторской модели — от 1000 приборов
- [ ] Модель предлагает 1–2 продукта, код проверяет правила и отбрасывает недопустимые
- [ ] Ответ объясняет выбор через слова клиента

**Готово, когда:**
- компании без АСКУЭ бот предлагает облачную платформу, а не поиск потерь;
- кафе не предлагает ОРЭМ;
- в рекомендациях только продукты из базы.

**Подводный камень:** держать критичные правила только в промпте. Модель иногда их нарушает — проверяет код.

## ⬜ Этап 5. Контакты и передача лида

**Цель:** полезный результат для менеджера.

- [ ] Согласие на обработку персональных данных до сбора контактов
- [ ] Контакты принимаются на любом этапе диалога, не только в конце
- [ ] `prompts/summary.md` + генерация лида по схеме из `docs/contract.md`
- [ ] `respond` возвращает `actions: [{"type": "handoff", "lead": {...}}]`
- [ ] Проверка лида по схеме перед возвратом

**Готово, когда:**
- после диалога в `leads/` появляется лид, который проходит проверку по схеме;
- по `summary` понятно, кому и с чем звонить, не читая переписку.

**Подводный камень:** модель «додумывает» поля. Всё, чего клиент не говорил, — `null`.

## ⬜ Этап 6. Сложные ветки

**Цель:** бот не ломается на нестандартных клиентах.

- [ ] Отказ давать контакты → анонимное резюме, предложение формы
- [ ] Сразу просит человека → сразу к контактам
- [ ] Вопрос не по теме → вежливо вернуть к сути
- [ ] Ничего не подходит → честно сказать и всё равно передать менеджеру
- [ ] Ошибка модели → запасной ответ из `docs/contract.md`

**Готово, когда:** каждая ветка проходит вручную хотя бы по разу.

## ⬜ Этап 7. Тестовый стенд

**Цель:** проверять качество цифрами, а не ощущениями.

Зависит от Виталия: тестовые клиенты.

- [ ] `evals/personas.yaml`: клиент, его ситуация, ожидаемый сегмент и продукт
- [ ] Модель-«клиент» разговаривает с агентом до конца диалога
- [ ] Проверки: сегмент, продукт, собраны ли контакты, число ходов, выдуманные факты (модель-судья сверяет с базой)
- [ ] `evals/run_evals.py` выводит таблицу и сохраняет результаты для сравнения «было / стало»

**Готово, когда:** одна команда прогоняет всех клиентов и показывает, кто прошёл, а кто нет.

**Подводный камень:** подгонять промпт под конкретные тесты. Правка, которая чинит один тест и ломает два, — не улучшение.

## Решения и заметки

Сюда записываем принятые решения, чтобы не обсуждать их заново.

| Дата | Решение | Почему |
|---|---|---|
| 2026-11-02 | Провайдер LLM — polza.ai | OpenAI-совместимый API, оплата в рублях |
| 2026-11-02 | Каталог услуг целиком в промпте, RAG только для больших документов | Продуктов около 10: модель видит все варианты сразу и не «промахивается» поиском |
| 2026-11-02 | Без LangChain, прямые вызовы API | Для агента с 2–3 инструментами проще и прозрачнее |
| 2026-11-03 | Модель — `deepseek-v4.1-flash`, рассуждения отключены (`reasoning: {"enabled": false}`) | JSON по схеме и инструменты работают; без рассуждений 1,6 с вместо 30 с на запрос |
